proofpage

Runs your repo's real test, typecheck, build and lint commands, then turns the result into one self-contained HTML page. It refuses to print any number it did not measure.

See a real one Source

MIT. Zero dependencies. Node 22+.

The first command in my README did not work, and 51 passing tests never noticed

proofpage shipped with 51 green tests. Its README opened with this:

proofpage --out examples/self-proof.html

A fresh install has no examples/ directory, and proofpage does not create one. So the first command a new user copy-pasted died with ENOENT.

Fifty-one tests could not catch it, and more tests in the same style never would have. They all run inside the repo, where examples/ exists because it is committed. The bug lived in the gap between "works on the author's machine" and "works on a machine that just installed it".

What caught it was a check that packs the tarball, installs it into a temp directory, and runs the README's first command there. It failed immediately.

That is the whole idea behind this tool: a test suite is a closed world, and some claims are claims about the world outside it.

What a page looks like

Every row is a command that actually ran, with the exit code it returned:

exit 0 npm test node:test summary parsed — 54 pass, 0 fail
exit 0 node scripts/lint.mjs output shape unrecognised — marked unparsed, not scored
did not run npm run typecheck no such script — no number is printed for it

That second row is the point. proofpage parses node:test and tsc output because those shapes are unambiguous. It guesses at nothing else, so its own lint script renders as unparsed rather than being given a score it did not earn.

The honesty law

  • A check that did not run shows no exit code and no count. Not 0 — nothing, with a line saying it did not run. 0 is a measurement, and printing it for "unknown" is the exact lie this tool exists to prevent.
  • Output that cannot be parsed with confidence is marked unparsed, with the reason.
  • If the working tree was dirty when the checks ran, the page says so next to the commit SHA. A receipt from an uncommitted tree is a receipt for code nobody else can check out.
  • If git is unavailable, the header says so rather than showing a fabricated commit.

Each of those is a test, not a policy.

The page fetches nothing

Zero JavaScript, zero network requests, and every <details> is open by default, because a collapsed one is dropped entirely when the page is printed to PDF. A receipts page that silently loses its evidence when printed is worse than no receipts page.

proofpage --check <file> enforces all of that mechanically, on any page, including one you did not generate. Every rule has a fixture that violates exactly that rule and a test asserting the check fails on it.

Use it

npx proofpage --out proof.html
npx proofpage --check proof.html

Exit 0 everything passed · 1 a check failed, which is the CI signal · 2 used wrongly, so nothing was measured and nothing is claimed.

What it will not tell you

  • Whether your tests are any good. A green proofpage page over a suite of empty tests is an honest report of a worthless suite.
  • Counts for anything other than node:test and tsc. Vitest, Jest and pytest shapes are not parsed yet.
  • Anything about a commit other than the one it measured. It is a snapshot, not a monitor, and it says which.
